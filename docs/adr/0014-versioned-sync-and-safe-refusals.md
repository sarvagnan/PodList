# Version sync changes and refuse unreadable operations

PurgePlaylist shipped with a new discriminator while the server still reported protocol 4. An older Android decoder rejected each pull, and an older server rejected a whole push with bare HTTP 400. Every wire change now increments the protocol version, whose frozen operation inventory and change description live in `packages/domain/src/Protocol.ts`. Version 5 adds PurgePlaylist and negotiation; the generated contracts, native constants and [versioned spec](../protocol/README.md) share that source. A version identifies a complete readable contract, including replay semantics, rather than a mutable collection of advertised extensions.

Clients declare their readable version in `x-podlist-protocol-version` on each sync push/pull. Undeclared means the deployed pre-purge version 4. A server serves each client only what its version can read: a pull containing newer operations returns HTTP 426 UpdateRequired with the minimum version, including when the client requests a snapshot. Unknown push discriminators return HTTP 422 UnsupportedOperation with the server version before any batch mutation. Clients never skip an unknown operation or advance a refused cursor. Emitters check the server version before enqueuing extensions and again before sending them; `supportedOperations` is removed from health because it duplicates the registry.

## Consequences

- Updated clients latch a compatibility pause on these errors or an unknown discriminator from an old server. They show “Update PodList to keep syncing” (or request a server update), keep queued edits, and resume only on manual retry or a new session. Native local editing stays available; web keeps its existing online-only, tab-memory behavior and closing warning.
- We reject partial replay and silently skipping unknown operations: either can lose intentions or corrupt later replay. Translating operations would need a proven semantic downgrade for every new type. Per-operation health flags fail to describe other wire changes and invite another missed rollout check.
- The server protects already-installed Android builds from the unknown discriminator by treating them as v4. It cannot change their existing generic HTTP error, retry scheduler or UI; installing the updated app is required for the clean pause. Future clients implementing this rule need no reader-first rollout ordering.
- v1–v3 are documented historical inventories; active negotiation supports v4 onward. Previously unversioned v4 additions are recorded as historical gaps. Every future optional field, endpoint and semantic wire change needs a version and response-shape gate, not just an operation inventory entry.
- Server downgrade across an operation already in its durable log is still unsupported. This decision protects sync peers and pending edits, without claiming to downgrade logs or databases.
